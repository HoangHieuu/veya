# Dataset (Person B)

Curated route records for scoring. **Person D** loads these files at runtime — B does not host an API.

## Layout

```
data/
├── version.json          { "datasetVersion": "0.4.0", "updatedAt": "..." }
├── routes/               9 files, one RouteRecord each: 3 origins × 3 destinations
│   ├── SYD-HAN.json
│   └── …
├── promotions/           empty — promotions are inline on each RouteRecord
├── assets/               gateway heroes + experience bento images
│   ├── *.jpg             one hero image per gateway (1920px)
│   ├── experiences/*.jpg one image per curated place (800px), when not reusing a hero
│   └── meta.json         every image → source, owner, licence, attribution line
├── experiences/          gateway → curated places (HAN.json, SGN.json, DAD.json)
├── need-place-map.json   need → place → gateway tags (Person B content)
├── fixtures/
│   ├── sampleIntent.json a TripIntent for D's scorer tests
│   └── expectedTop3.json the ranking that intent must produce
└── tools/
    └── validate-dataset.mts  pre-merge gate
```

## Schema

Each route file must match `RouteRecord` in [`shared/types.ts`](../shared/types.ts).

Required for MVP: `indicativeFareBand`, `bestMonths`, `gettingAround`, `dataConfidence`, `backgroundImage.licenseNote`.

Experience highlights in `experiences/*.json` match `ExperienceHighlight` in `shared/types.ts` and are loaded by the API into `RankedCard.experienceHighlights`.

## Versioning

When you change routes, bump `datasetVersion` in `version.json`. D must echo the same value in `RankedResponse.meta.datasetVersion`.

### Topology, and why

Derived from the Lotusmiles published sector table, which lists only sectors Vietnam Airlines
actually operates. The Australia sectors present are SYD-HAN, SYD-SGN, MEL-HAN, MEL-SGN and
PER-SGN — there is no Australia-Da Nang sector, and no PER-HAN or PER-DAD. The VNA Melbourne-to-Da
Nang page says so in words: *"nonstop flights are not available... connecting options, often via
major transit hubs in Hanoi or Ho Chi Minh City."*

| | HAN | SGN | DAD |
|---|---|---|---|
| **SYD** | direct | direct | one stop via SGN |
| **MEL** | direct | direct | one stop via SGN |
| **PER** | one stop via SGN | direct | one stop via SGN |

Every origin therefore has three routes at one stop or fewer, so all three return three cards for
every priority preset. `maxStops: 0` fires only on a literal "direct only" brief
(`apps/api/src/intent/briefHeuristic.ts:179`) — **Person D does not need to change
`filterCandidates`.**

### Field provenance

| Field | Basis |
|---|---|
| `connectionType`, `viaHub` | Lotusmiles sector table + VNA route-page wording |
| `typicalDurationHours` | VNA route pages for SYD-SGN, MEL-HAN, MEL-SGN, MEL-DAD, PER-SGN. **Derived** for SYD-HAN, SYD-DAD, PER-HAN, PER-DAD — VNA publishes no figure; each record says so in `sourceDocument`. |
| `indicativeFareBand` | Tercile of a nine-route AUD snapshot captured 2026-09-12 from the VNA `/en-au` route pages. **Relative within this curated set, not a live price.** |
| `lotusmilesIndicative` | Lotusmiles published sector distances. `low`/`mid`/`high` is a **Veya internal signal, not a Lotusmiles tier**; accrual depends on booking class, so the note never promises a mileage figure. |
| `promotion` | LotuStudents, verified on both the `/au/en/` and `/in/en/` pages. Tier 1 (20% off Economy Lite, ticketing to 31/10/2026) on the five direct AU-HAN/SGN routes; tier 2 (10% off, ticketing to 31/12/2026) on the four connecting routes, since tier 1 excludes multi-segment itineraries. |
| `bestMonths`, `shoulderMonths`, `seasonalityNotes`, `gettingAround` | Regional climate and airport-transfer facts, not VNA claims. |

`dataConfidence` is `illustrative` on all nine: confirming schedules with Vietnam Airlines is still
an open question in the proposal, so nothing here claims to be confirmed.

### Known consequences, deliberately not tuned away

- **Olivia ranks Hanoi first and Da Nang third.** She wants beach and food in mid-November, and
  November is Da Nang's wet season, so `dateFit` scores 40 there despite a perfect `intentMatch`
  of 100. The UI mock shows Da Nang first. The dataset is not being bent to match the mock.
- **`promotionBoost` no longer discriminates.** All nine routes carry a real, in-date LotuStudents
  tier, and `scorePromotion` is binary (in date -> 100, otherwise 0), so every route scores 100.
  The factor is accurate but contributes nothing to ranking. Fixing that is a scoring-engine
  question for Person D, not a dataset one.

### Validating before merge

The loader **skips a malformed route file silently** — it logs `ROUTE_INVALID` and moves on — so a
broken record shows up as a missing card rather than an error. Always run the gate first:

```bash
cd apps/api && npm install                                  # once: provides zod + tsx
apps/api/node_modules/.bin/tsx data/tools/validate-dataset.mts
```

It imports Person D's real `loadDataset()` and `routeRecordSchema`, so it cannot drift from what
the API enforces. Beyond schema validity, duplicate IDs and 9/9 coverage it checks four things the
schema does not:

- **`maxStops` is a hard filter, not a penalty.** `filterCandidates()` drops any route with more
  stops than the intent allows, so each origin needs three routes within the cap to fill three
  cards. A shortfall at `maxStops: 0` is only a warning — a "direct only" brief genuinely has
  fewer options.
- **A constant field is a dead scoring factor.** If all nine routes share one
  `indicativeFareBand`, `budgetFit` returns the same number for every one of them and stops
  ranking anything. Same for an all-`null` `promotion` or `lotusmilesIndicative`.
- **Every `backgroundImage.url` and experience `imageUrl` has a file** committed under `assets/`.
- **`expectedTop3.json` matches the current `datasetVersion`**, so a stale lock cannot pass.

### Regenerating

`expectedTop3.json` is generated, never edited by hand: start the API, POST each persona's intent
as `cachedIntent` to `/api/recommend`, and record the cards. Re-run it whenever `datasetVersion`
changes — the gate fails on a stale lock.

It covers three personas, each carrying its own intent so D needs no second file:

| Persona | Intent from | Cards | Result |
|---|---|---|---|
| `olivia` | `data/fixtures/sampleIntent.json` | 3 | SYD-HAN 81.5, SYD-SGN 81.3, SYD-DAD 74.5 |
| `student` | `fixtures/briefs/student.json` | 3 | PER-SGN 90.8, PER-DAD 86.3, PER-HAN 85.8 |
| `vfr` | `fixtures/briefs/vfr.json` | **1** | MEL-HAN 83 |

The VFR case returning one card is **correct, not a bug**: `goal: "choose_route"` with
`preferredDestination: "HAN"` filters to that destination. `meta.disclaimer` must explain the short
list rather than stay silent.

## Gateway experiences (agent destination board)

`experiences/HAN.json`, `SGN.json` and `DAD.json` each carry curated places for the agent
destination board, with `transferNote` for ground time (Hoi An via DAD, Vũng Tàu via SGN, Ha Long
Bay, Ninh Binh, and similar).

Each highlight uses `tags` (`food`, `beach`, `quiet`, `family`, `culture`, `city`) so the UI
quick-refine chips can filter and reorder without another round trip. Person D loads these into
`RankedCard.experienceHighlights` at recommend time.
